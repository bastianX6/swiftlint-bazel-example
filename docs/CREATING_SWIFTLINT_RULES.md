# Creating SwiftLint Rules in this repo

This guide explains how to add native SwiftLint rules in this Bazel setup.
It targets both humans and LLM agents and goes beyond the minimal example.

## 1) Architecture in this repository

- This repo builds a **custom SwiftLint binary** with Bazel.
- Files in `swiftlint_extra_rules/` are compiled into that binary.
- `extra_rules.swift` is generated by Bazel from those files.

If your rule file is under `swiftlint_extra_rules/` and compiles, it is included automatically.

## 2) Rule model: which protocol/type to use

SwiftLint exposes multiple rule styles. Most custom rules here should start as `@SwiftSyntaxRule`.

| Type | Use when | Notes |
|---|---|---|
| `Rule` | Base protocol for all rules | Requires `description` and `configuration` |
| `SwiftSyntaxRule` | AST-based lint rule (recommended default) | SourceKit-free by default |
| `SwiftSyntaxCorrectableRule` | SwiftSyntax rule that can autocorrect | Usually via `@SwiftSyntaxRule(correctable: true)` or `explicitRewriter: true` |
| `CorrectableRule` | General correction-capable rule | Used by non-SwiftSyntax implementations too |
| `AnalyzerRule` | Needs compiler/type-check context | Requires analyzer mode + compiler args |
| `CollectingRule` | Needs cross-file collected info | Two-phase pattern: collect then validate |
| `SourceKitFreeRule` | Explicitly marks no SourceKit dependency | Many SwiftSyntax rules are naturally SourceKit-free |
| `ConditionallySourceKitFree` | SourceKit availability depends on config | Advanced/rare custom scenario |

## 3) `@SwiftSyntaxRule` macro parameters

`@SwiftSyntaxRule` auto-generates protocol conformances and helpers around your `Visitor`/`Rewriter`.

```swift
@SwiftSyntaxRule(
    foldExpressions: false,
    explicitRewriter: false,
    correctable: false,
    optIn: false
)
```

- `foldExpressions`: pre-folds expressions before visiting.
- `explicitRewriter`: generates `makeRewriter(file:)` and expects a `Rewriter` type.
- `correctable`: marks the rule correctable even without explicit rewriter.
- `optIn`: makes the rule conform to `OptInRule` (disabled unless explicitly enabled).

## 4) `RuleDescription` fields that matter in practice

At minimum, define:

- `identifier`: stable snake_case ID (part of public config contract)
- `name`: readable title
- `description`: short behavior summary
- `kind`: usually `.lint`, sometimes `.style`, `.metrics`, etc.
- `nonTriggeringExamples`
- `triggeringExamples`

Useful advanced fields:

- `rationale`: why this rule exists
- `corrections`: before/after examples for autocorrection
- `aliases`: backward-compatible IDs
- `minSwiftVersion`: if rule requires newer language syntax
- `requiresFileOnDisk`: true when analysis needs on-disk file context

## 5) Configuration patterns

### 5.1 Default severity-only rule

```swift
var configuration = SeverityConfiguration<Self>(.warning)
```

### 5.2 Warning/error thresholds

Use `SeverityLevelsConfiguration` when warning and error values differ (for example max length rules).

### 5.3 Custom structured config (`@AutoConfigParser`)

```swift
import SwiftLintCore

@AutoConfigParser
struct NoPrintConfiguration: SeverityBasedRuleConfiguration {
    @ConfigurationElement(key: "severity")
    private(set) var severityConfiguration = SeverityConfiguration<Parent>(.warning)

    @ConfigurationElement(key: "allow_in_tests")
    private(set) var allowInTests = false
}
```

`@ConfigurationElement` supports scalar and collection values (for example `Bool`, `String`, `Int`, `Double`, arrays/sets, regex wrappers, and nested `RuleConfiguration` values).

## 6) Practical examples

### 6.1 Basic SwiftSyntax lint rule (visitor only)

```swift
import SwiftLintCore
import SwiftSyntax

@SwiftSyntaxRule
struct NoPrintRule: Rule {
    var configuration = SeverityConfiguration<Self>(.warning)

    static let description = RuleDescription(
        identifier: "no_print",
        name: "No Print",
        description: "Avoid print(...) in committed code",
        kind: .lint,
        nonTriggeringExamples: [
            Example("logger.info(\"hello\")"),
        ],
        triggeringExamples: [
            Example("↓print(\"debug\")"),
        ]
    )
}

private extension NoPrintRule {
    final class Visitor: ViolationsSyntaxVisitor<ConfigurationType> {
        override func visitPost(_ node: FunctionCallExprSyntax) {
            guard
                let called = node.calledExpression.as(DeclReferenceExprSyntax.self),
                called.baseName.text == "print"
            else {
                return
            }
            violations.append(node.positionAfterSkippingLeadingTrivia)
        }
    }
}
```

### 6.2 Correctable rule with explicit rewriter

Use when you want deterministic source rewriting (pattern used by built-in correctable SwiftSyntax rules).

```swift
@SwiftSyntaxRule(explicitRewriter: true)
struct RenameFooRule: Rule {
    var configuration = SeverityConfiguration<Self>(.warning)

    static let description = RuleDescription(
        identifier: "rename_foo",
        name: "Rename Foo",
        description: "Rename variable 'foo' to 'bar'",
        kind: .style,
        nonTriggeringExamples: [Example("let bar = 1")],
        triggeringExamples: [Example("let ↓foo = 1")],
        corrections: [Example("let foo = 1"): Example("let bar = 1")]
    )
}

private extension RenameFooRule {
    final class Visitor: ViolationsSyntaxVisitor<ConfigurationType> {}

    final class Rewriter: ViolationsSyntaxRewriter<ConfigurationType> {
        // Implement AST rewrite and increment numberOfCorrections when applying a fix.
    }
}
```

### 6.3 Analyzer rule (compiler-aware)

Use when syntax alone is insufficient (for example unused declarations/imports with type-check context).

```swift
struct MyAnalyzerRule: Rule, AnalyzerRule {
    var configuration = SeverityConfiguration<Self>(.warning)
    static let description = RuleDescription(
        identifier: "my_analyzer_rule",
        name: "My Analyzer Rule",
        description: "Analyzer-only check",
        kind: .lint,
        requiresFileOnDisk: true,
        nonTriggeringExamples: [Example("let x = 1")],
        triggeringExamples: [Example("↓let y = 2")]
    )

    func validate(file: SwiftLintFile,
                  compilerArguments: [String]) -> [StyleViolation] {
        // Analyze with compiler context.
        []
    }
}
```

### 6.4 Collecting rule (multi-file behavior)

Use when violations depend on data aggregated across files.

```swift
struct MyCollectingRule: Rule, AnalyzerRule, CollectingRule {
    typealias FileInfo = [String]
    typealias CollectedInfo = [String: [String]]

    var configuration = SeverityConfiguration<Self>(.warning)
    static let description = RuleDescription(
        identifier: "my_collecting_rule",
        name: "My Collecting Rule",
        description: "Collects info per file, validates globally",
        kind: .lint,
        nonTriggeringExamples: [Example("let x = 1")],
        triggeringExamples: [Example("↓let y = 2")]
    )

    func collectInfo(for file: SwiftLintFile,
                     compilerArguments: [String]) -> FileInfo {
        []
    }

    func validate(file: SwiftLintFile,
                  collectedInfo: CollectedInfo,
                  compilerArguments: [String]) -> [StyleViolation] {
        []
    }
}
```

## 7) Build wiring in this repo

You normally do **not** edit Bazel wiring for each new rule.

- `swiftlint_extra_rules/BUILD` already exposes all `.swift` files via `filegroup`.
- A `genrule` builds generated `extra_rules.swift`.
- `MODULE.bazel` already passes that filegroup to SwiftLint.

Only add your new rule source file under `swiftlint_extra_rules/`.

## 8) Validation workflow

Run from repo root:

```bash
bazel run -c opt @SwiftLint//:swiftlint
bazel run -c opt @SwiftLint//:swiftlint -- version
bazel test --test_output=streamed @SwiftLint//Tests:ExtraRulesTests
```

Optional sanity check for registration:

```bash
bazel run -c opt @SwiftLint//:swiftlint -- rules | grep <rule_identifier>
```

## 9) Common failure modes

- Editing generated `extra_rules.swift` manually.
- Rule `identifier` churn (breaks user config compatibility).
- Missing non-triggering examples (false-positive risk).
- Wrong violation location token/position.
- Using `AnalyzerRule` when a pure SwiftSyntax visitor is enough.
- Adding complex config before proving the minimal rule behavior.

## 10) LLM playbook (copy/paste)

When an LLM adds a rule, it should execute this sequence:

1. Create exactly one new `.swift` file in `swiftlint_extra_rules/`.
2. Default to `@SwiftSyntaxRule` + `SeverityConfiguration` unless a stronger need exists.
3. Add `RuleDescription` with stable `identifier` and both example sets.
4. Add minimal `Visitor` logic first, then refine matching.
5. Use `explicitRewriter: true` only for deterministic, safe fixes.
6. Avoid touching generated files or unrelated Bazel/module config.
7. Run at least one Bazel command before finishing.
8. Keep edits targeted and explain trade-offs (false positives vs missed detections).
